# Advisor pressure-test of the project plan — 2026-07-09

Adversarial review of the initial architecture (CM1 → Python pipeline → UE5 SVT
playback) performed before any implementation started. All findings below were
incorporated into the root CLAUDE.md. Preserved verbatim.

---

## (a) Verdict

The architecture is fundamentally sound and the tool choices are defensible — CM1 is the right core, the WSL/ext4 discipline is correct, and the "UE is a dumb player" split is exactly right. But the plan contains **two mutually exclusive features presented as compatible optimizations (moving domain + terrain)**, **one optimization that is a no-op (single-precision build — that's already CM1's default)**, an **optimistic overnight estimate for 250 m** that will likely be 15–30 hours with NSSL 2-moment, and it **underestimates the UE5 SVT pipeline risk** — SVT is still officially Experimental, has an 8-channel/2-texture budget, degrades above ~30–50 MB/frame, and the obvious fallback plugin (Eidos unreal-vdb) has been archived since June 2023. None of these kill the project; all of them will burn weeks if discovered mid-phase instead of now.

## (b) Corrections and risks, ranked by severity

1. **Moving domain and terrain are mutually exclusive.** CM1's `imove` translates the whole grid at constant `umove`/`vmove` ([CM1 namelist docs](https://cm1.readthedocs.io/en/latest/README.namelist/)); terrain in CM1 is fixed to the grid via the Gal-Chen transform ("model surfaces… are fixed in space", [README.terrain](https://github.com/george-bryan/CM1/blob/main/README.terrain)). You cannot translate a grid that has terrain bolted to it. The plan lists both "moving domain" and "modest terrain" as if they compose. Decide per-scenario-class: flat scenarios get a moving (smaller) domain; terrain scenarios eat a full-size static domain and a longer run. Budget accordingly. Also: there is no `pt_move` in CM1 — the option is `imove=1` with **constant** prescribed motion, not storm-following. You must estimate storm motion a priori (Bunkers right-mover from the hodograph) and accept drift; supercells that deviate will walk toward the domain edge.

2. **"Overnight at 250 m on 8 cores" is optimistic; treat 15–30 h as the planning number.** See Q3 below for the arithmetic. The single biggest schedule risk in the project is discovering this in Phase 3. Mitigation: make Phase 0 produce a measured cell-steps/second number at 1 km and extrapolate (×~64 from 1 km to 250 m at fixed domain/duration) before any promise about final resolution. Consider 333–500 m as the realistic "final" resolution, or shrink domain/duration.

3. **UE5 SVT is Experimental with hard limits you're near.** Per [Epic's SVT docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/sparse-volume-textures-in-unreal-engine): max **two attribute textures (A/B), 8 channels total**; page table capped at 2 GB, virtual resolution 32k×32k×16k; **streaming degrades above ~30–50 MB per frame**; "use caution when shipping"; all grids in a frame must share identical transforms; community reports of long import times and editor crashes on multi-grid sequences, and a requirement that the bounding-box center be static across the animation ([versluis.com](https://www.versluis.com/2025/03/how-to-use-vdbs-in-unreal-engine/)). Your channel demand (cloud condensate, ice, rain, graupel/hail, dBZ, maybe temperature for shading) must be explicitly budgeted into 8 channels with matched transforms and a fixed, padded bounding box across all frames. The fallback plugin, [eidosmontreal/unreal-vdb](https://github.com/eidosmontreal/unreal-vdb), is **archived (June 2023)** and unmaintained — do not list it as a safety net without a test on your UE version. Phase 1 should be a de-risking spike: one real multi-grid, few-hundred-frame sequence through SVT before committing UI architecture to it.

4. **"Single-precision build of CM1" is not an optimization — it's the default.** CM1 builds with 4-byte reals unless you enable double precision (`-DDP`). Remove it from the wins list; the run-time budget must assume you're already single precision. (Moderate confidence on the flag name; high confidence single is default.)

5. **"Half precision output" is not a thing in netCDF/CM1.** CM1 writes float32 (GrADS or netCDF, `output_format=1/2`). The real levers are: fewer 3D fields, lower frequency for non-key fields, netCDF-4 deflate/chunking (or post-compress with `nccopy`), and int16 scale/offset packing in the post-processor. Same intent, different mechanism — rewrite the plan item.

6. **pyopenvdb is the flakiest link in the pipeline.** PyPI wheels are stale (Python 3.7/3.8 era, [pypi](https://pypi.org/project/pyopenvdb/)); building from source needs Boost/TBB/pybind11 and is famously tedious ([ytini guide](http://www.ytini.com/tutorials/tutorial_vdbInstall.html)). Mitigations in order: Ubuntu's `python3-openvdb` apt package inside WSL (pin the distro Python to match), conda-forge openvdb, or a small standalone C++ dense-array→VDB converter (~200 lines) that the Python pipeline shells out to — honestly the most robust option and worth doing anyway. Do not write "pyopenvdb" into the contract; write "VDB writer, implementation documented in pipeline/".

7. **Weisman–Klemp gives you CAPE and shear knobs, but not an independent CIN knob.** Your forecast panel promises CIN as a storm-development condition; the classic WK analytic sounding has weak, incidental CIN. You'll need a modified analytic profile (e.g., McCaul–Weisman-style buoyancy redistribution, or a capped mixed layer added to WK) to dial CIN while holding CAPE. This is a real design task, not a config value — currently missing from the plan.

8. **Vertical exaggeration as "one Z-scale on a root container" will break more than it fixes.** Non-uniform scale on a parent distorts: text/annotation glyphs (stretched), Niagara particle fall speeds and sprite shapes (rain streaks become wrong), and possibly Heterogeneous Volumes ray-march step assumptions under non-uniform actor scale (untested territory in an Experimental feature — verify early). The *principle* (never bake exaggeration into data) is right; the *mechanism* needs counter-scaled billboards/labels and velocity-compensated particles.

9. **Playback smoothness vs output frequency is unaddressed.** At a realistic 10–30 s output interval you get ~240–720 frames for a 2 h storm. SVT plays discrete frames flipbook-style; time-compressed playback will visibly step unless you either output more frames (disk/IO cost — at ~2×10^7 cells, ~1 GB+ per frame raw before decimation, i.e., 300 GB–1 TB raw per scenario) or interpolate/crossfade between frames in the material. Pick one now; it affects both output config and UE material design.

10. **Reproducibility promise is stronger than what you can cheaply guarantee.** Bit-identical reruns require pinning binary, flags, rank count **and domain decomposition**, and even then floating-point reduction order can bite. Verify bitwise reproducibility once in Phase 0; if it fails, downgrade the contract to "statistically equivalent storm" and record checksums of outputs instead.

11. **WSL2 resource config is missing.** Default WSL2 caps memory (typically 50% of RAM) — set `.wslconfig` (e.g., 48 GB, 16 CPUs). The ext4 VHDX lives on the system drive by default; a 300 GB–1 TB per-scenario raw output will fill it. Relocate the distro or mount a dedicated VHDX on the multi-TB drive. Also set `rstfrq` for restart files so a crash at hour 18 of a 24 h run isn't a total loss.

12. **Licensing: fine but verify once.** CM1 is free to download and modify ([NCAR/CM1 LICENSE exists](https://github.com/NCAR/CM1/blob/main/LICENSE)); you're distributing outputs, not code, so risk is low — but read the LICENSE file once and note it in docs/. NSSL scheme and parameterization papers need citation only.

## (c) The six questions

**1. Is CM1 the right core?** Yes, and it's not close. Alternatives: WRF idealized (`em_quarter_ss`) — heavier build, slower, more moving parts, no benefit here; SAM — anelastic, restrictive access; RAMS — dated tooling; PALM/MicroHH — LES-focused, lack hail-grade ice microphysics; FastEddy — GPU-resident (tempting given the idle RTX 5090) but its microphysics can't do NSSL-grade hail, so it fails your hail requirement. CM1 is purpose-built for exactly this: idealized convection, analytic WK soundings built in, NSSL 2-moment included, terrain support, tiny build surface, runs fine in WSL2. One honest note: your 5090 sits completely idle during simulation, and there is no production-ready GPU cloud model with the microphysics you need — accept that or treat a GPU port as out of scope.

**2. Factual errors.** The material ones are items 1, 4, 5 above (`pt_move` doesn't exist / imove is constant-motion only and incompatible with terrain; single precision already default; half-precision output not a thing). Verified correct: `adapt_dt` exists; NSSL 2-moment is `ptype=26/27` — **you must use 27** (26 is graupel-only, no hail category); `output_dbz` is available for ptype 26–28; netCDF output via `output_format=2`; WK sounding and warm-bubble init with random perturbations are standard CM1. UE side: SVT VDB import exists since 5.3 and does handle sequences, but see limits in item 3. One subtlety: with terrain, CM1 output is on terrain-following surfaces — your post-processor must interpolate to Cartesian z before VDB export or your volumes will be warped; CM1's built-in interpolation option is self-described as "quick-and-dirty" ([README.terrain](https://github.com/george-bryan/CM1/blob/main/README.terrain)) — do it properly in Python.

**3. Is 250 m overnight on 8 cores realistic?** Rough honest arithmetic: 100×100 km at 250 m = 400×400 columns; ~110–130 stretched levels to 20 km ≈ 2×10^7 cells. dt ≈ 1–2 s at this resolution → ~5,000–9,000 steps for 2–3 h of storm time ≈ 1–1.8×10^11 cell-steps. A 7800X3D running CM1+NSSL (an expensive scheme: 2 moments × ~6 species plus predicted densities) will be memory-bandwidth-limited (dual-channel DDR5; the V-cache helps less than you'd hope on multi-GB working sets); realistic aggregate throughput ~1.5–3×10^6 cell-steps/s → **roughly 12–30 hours**. That's "borderline overnight" at best. Which optimizations are real:
- **Real, big:** iterate at 1 km / finalize once (the 64× ratio is the whole game — but beware storms changing character between 1 km and 250 m; add a 500 m sanity pass); reduced/compressed output (I/O and disk, not CPU); vertical **stretching** (50 m near surface → 300–400 m aloft cuts levels vs uniform 150 m and is better science); `adapt_dt` (real, modest, ~10–30%).
- **Real, constrained:** moving domain (flat scenarios only, item 1) — can cut domain area 2–4×, the second-biggest lever where usable; horizontal stretching (helps only if the storm stays in the fine patch — over 2–3 h without a moving domain it often won't).
- **Wishful/no-op:** single-precision build (already default); half-precision output (doesn't exist); SMT/16 threads (memory-bound code — expect zero or negative; benchmark 6 vs 8 ranks).
- **Missing from your list:** run **two scenarios concurrently at 4 ranks each** overnight — on bandwidth-bound code this often beats one 8-rank run in total throughput; and MPI vs OpenMP: on one node use plain MPI (CM1's MPI path is the battle-tested one; OpenMP historically weaker) — benchmark once in Phase 0 and stop thinking about it.

**4. Lightning vs constraint #1: acceptable, with the right framing.** The constraint says parameters affecting *storm development* must act through simulation. Lightning in this design has **no feedback on storm development** — it's a diagnostic, exactly like radar reflectivity (which is also a parameterized diagnostic from microphysics, and nobody objects to that). Frame it precisely that way in docs and UI: "diagnosed quantities (dBZ, flash rate) are computed from simulated microphysics via published parameterizations (McCaul et al. 2009); they do not influence the simulation." The chain is still honest physics: more CAPE → stronger updraft → more graupel flux → more flashes, all through the model. Middle path (explicit electrification): NSSL's schemes exist in COMMAS and WRF-ELEC, not in stock CM1; adopting them means switching or patching models, ~30–50%+ extra cost including an elliptic solver for the electric field, for a visual result your audience can't distinguish. Not worth it for v1; note it in docs/ as a considered-and-deferred option. One requirement to add: flash *origin placement* (graupel–ice interface regions) should be computed in the pipeline and shipped as data (event list with positions/times/polarity), not invented in Niagara — keeps UE dumb and the science auditable.

**5. Missing from the plan entirely:**
- **CIN-controllable sounding generator** (item 7) — a genuine science-code task.
- **Phase 0 benchmark gate** with a go/no-go on final resolution (item 2).
- **Frame-time interpolation strategy** for smooth time-compressed playback (item 9).
- **SVT channel/transform budget** and fixed padded bounding box across the sequence (item 3).
- **Coordinate/units contract**: CM1 is meters, z-up, right-handed; UE is centimeters, Z-up, left-handed (Y flip). Define the transform in exactly one pipeline module or you'll chase mirrored hodographs forever.
- **Terrain-to-Cartesian regridding** in the post-processor (Q2).
- **WSL config**: `.wslconfig` memory/CPU, VHDX location on the big drive, restart files (item 11).
- **Multicell initiation design**: one warm bubble gives one cell; multicell needs multiple bubbles/line forcing/random low-level perturbations — a scenario-design decision, not a slider.
- **Skew-T/hodograph rendering**: generate them as images in the Python pipeline (MetPy/matplotlib) and ship in the package rather than drawing in UMG — consistent with "UE is a dumb player" and vastly less UE work.
- **Niagara data feed**: Niagara sampling SVTs is dicey; bake near-surface qr/qg into the 2D surface-texture stack and drive particles from that.
- **Git/data policy**: raw netCDF is regenerable and never committed; scenario packages are multi-GB — decide LFS vs outside-repo now.
- **Validation criterion for Phase 0**: compare against published WK supercell evolution (updraft max, splitting time) so "it ran" isn't confused with "it's right."

**6. netCDF→VDB→SVT pipeline risk: real, and the plan is too breezy about it.** Known pain points: pyopenvdb installation (item 6); VDB grid naming/transform requirements and no-periods-in-filenames on UE import; long import times and editor instability for multi-hundred-frame multi-grid sequences; the static-bounding-box-center requirement; the 30–50 MB/frame streaming cliff, which becomes your decimation budget; Experimental-status churn between UE versions (pin the UE version); and Heterogeneous Volumes' real-time limitations (shadowing/scattering quality is path-tracer-first; real-time is "partly limited by deferred rendering features" per Epic). None are fatal; all argue for Phase 1 being explicitly a pipeline-proving spike with a full-length real sequence, not a one-frame demo. Keep the archived Eidos plugin only as a tested-or-discarded fallback.
