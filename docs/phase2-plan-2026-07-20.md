## 2. Advisor corrections taken

### 2.1 The second scenario stays single-cell — a sheared storm is Phase 3

The original plan had a deliberately *sheared* second scenario, justified as the
known-asymmetric test asset that Phase 1 carried item #1 demands for the Y-flip. The
advisor killed both halves of that:

- **Phase boundary.** The charter puts "multicell/supercell scenarios" in Phase 3. A
  storm sheared enough to be an *unambiguous* handedness test is organized-regime
  physics pulled forward.
- **The motivation evaporated.** Carried item #1 requires the Y-flip be verified "before
  Phase 2 **placement code** ships" — that is the UE actor `scale.y = -100`. The owner
  deferred UE, so nothing in this phase ships placement code. **Carried item #1 is
  therefore deferred with the UE app, not discharged here.**

The second scenario exists to make "selectable" mean something and to exercise the config
parameterization — which is the actual goal. Single-cell regime, 500 m preview tier.
If it carries mild asymmetry, that is a free sanity-check on the *diorama's* own
E-W/N-S orientation (a bug the axisymmetric Phase 1 cell would mask) — a bonus, not a
reason to build a supercell.

### 2.2 The regression gate is on decoded arrays, not VDB bytes

VDB files are not guaranteed byte-reproducible (embedded metadata, library version
strings, compression ordering), and the manifest changes *by design* this phase. A
byte-diff gate would fail spuriously. The gate is therefore:

- **decoded voxel arrays** (`.densevol` / pre-writer numpy) **identical**, and
- **manifest identical except the fields deliberately changed.**

### 2.3 "Radar view" and "layers" had to be pinned before T5/T6, not assumed

Recorded above in §1. The risk the advisor flagged was assuming the diorama's existing
dBZ layer already *was* the radar view. It is not — an earlier advisor caught and the
design doc records that it is peak dBZ along the **view ray**, explicitly not composite
reflectivity. Both will now exist, and must stay distinctly labelled (T9).

## 4. The scenario system's central design decision

The refactor splits today's single `pipeline/cm1post/config.py` in two, along the line
between *what is frozen by the format contract* and *what varies per scenario*. Getting
this line right is the whole point: putting a frozen quantity in the per-scenario JSON
invites someone to change it per scenario and silently break the SVT import contract.

**`cm1post/contract.py` — frozen, one per `format_version`, NOT per scenario:**
channel names and order, `SOURCE_FIELDS`, activity thresholds, diagnostic-channel set,
the SVT texture map, encodings. Task 3 proved UE 5.8's default grid→SVT assignment
reproduces this map exactly; *changing a channel name forces an SVT import re-test*.
Thresholds live here too because the padded bbox is sized at these values — a per-scenario
override would decouple the sweep from the export and silently clip the storm.

**`cm1post/scenario.py` — per-scenario, loaded from `sim/scenarios/<name>.json`:**
name, kind, description, run dir, export voxel size, crop half-width and z-top, and the
CM1 deck parameters. `NX/NY/NZ/ORIGIN_M` become derived properties rather than module
constants.

**CM1 deck generation is template + overrides, not full generation.** The validated
namelist has ~8 KB of parameters that must not drift. The scenario JSON specifies only
what it changes (`nx`, `dx`, `iwnd`, …); the generator applies those over the validated
base template and records which keys it overrode. This gives a second regression gate:
**the generated `single_cell_500m` deck must reproduce the committed hand-written
`sim/single_cell/namelist.input`** (modulo comments and key ordering).

## 7. Decision — `w` and `cref` are WEB-EXPORT-ONLY this phase

Taken 2026-07-20 after the advisor flagged that the contract frozen in T1 assumes five
uniform, non-negative, log-encoded **volume** channels, and neither new field fits it:
`cref` is 2D, and `w` is signed.

**`contract.CHANNELS` and `SVT_TEXTURE_MAP` stay untouched.** `w` and `cref` are added
to the web export only. The reasoning is not aesthetic:

- The diorama — this phase's only player — consumes the **web export**, not the VDB.
- Adding a channel to `contract.CHANNELS` pulls in the SVT texture map and RGBA
  packing that **only the deferred UE app** uses.
- `contract.py` states that changing the channel map *forces an SVT import re-test*.
  That re-test cannot happen this phase: the editor is owner-gated, and Phase 1's
  most load-bearing lesson is that `-nullrhi` is **structurally incapable** of
  validating it.

So the UE-facing contract stays frozen until it can actually be re-verified. When the
UE app is built, promoting `w` into the SVT path is a deliberate, re-tested change —
Tex B has 3 spare channels (G/B/A) waiting for exactly this.

This means the export grows a second path — "extra CM1 vars → web export" — distinct
from the five-channel `build_channels` path. That is the intended shape, not a wart.

## 8. T1b gate results (2026-07-20)

Four gates, all passing. T1 was deliberately built as a **pure refactor with zero
output change**, which is what makes exact byte-identity available as a gate instead of
the weaker "identical except the fields we meant to change".

| Gate | Method | Result |
|---|---|---|
| A — VDB manifest | `manifest.build()` is a pure function of (Scenario, frames, provenance); rebuilt the shipped 48 KB manifest from the scenario config + shipped frame records | **PASS** — byte-identical, 34810 chars. Grid derives to 208×208×72 @ 250 m, origin (−25875, −25875, 125) |
| B — VDB arrays | Pre-refactor pipeline extracted from git via `git archive` (no worktree, repo metadata untouched), run head-to-head on frames 150:153 | **PASS** — `.densevol` byte-identical, 62 300 266 bytes each |
| A — web manifest | Same pure-function trick; `qmax` recovered from the shipped manifest's own `channels[].qmax` / `dbz.vmax` | **PASS** — byte-identical, 45381 chars |
| B — web arrays | Same `git archive` A/B, frames 150:153 | **PASS** — 6 brick files identical |

Two method notes worth keeping:

- **Gate on the data, never the container.** `.vdb` is not guaranteed byte-reproducible
  (embedded metadata, library version strings, compression ordering), and `.gz` carries
  an **mtime in its header** — Python's `gzip` stamps it, so two runs over identical
  data produce different `.gz` bytes. Both gates therefore compare the *decompressed*
  / pre-writer arrays. A naive `cmp` on either container would have failed spuriously
  and cost an afternoon.
- The web path was nearly shipped un-run: it received the same signature edits as the
  VDB path and *read* correct. Since Phase 2 is diorama-first, a latent regression there
  would have surfaced late and far from its cause. "Reads correct" is not "ran".

## 10. T1c — CM1 deck generator (DONE 2026-07-20)

`pipeline/cm1post/deck.py` + `pipeline/gen_deck.py` + `sim/templates/base.namelist.input`.
The scenario JSON now drives both halves: the same config that exports a package also
generates the deck that produced it, so a scenario cannot be *simulated* with one
geometry and *exported* with another.

### 10.1 The keys are four categories, not one

The diff between the two committed decks is 17 lines, and planning treated them as
one bucket. They are not — and only the first belongs in the scenario JSON:

| Category | Source | Keys |
|---|---|---|
| Scenario identity | JSON `sim.namelist`, **required** | grid, timing, `isnd/iwnd/iinit/irandp/icor/imove/iorigin`, `ptype/ihail`, terrain |
| Geometry-derived | generator computes | `dx_inner`, `dy_inner`, `tot_x_len`, `tot_y_len` |
| Motion-coupled | forced 0 at `imove=0`; required at `imove=1` | `umove`, `vmove` |
| Output block | template DNA, verbatim | `&param9` |

**The output block is asserted, never generated.** Deriving `&param9` from
`contract.SOURCE_FIELDS` is the tempting move and it is wrong: the validated deck
writes considerably more than the exporter reads (`tke`, `km`/`kh`, `uh`, `vort`,
`lcl`/`lfc`/`pwat`) and the validation/analysis scripts use those extras, so
deriving would shrink the deck and break the reproduction gate. The contract is
applied as `deck.check_output_flags` instead — `output_q`, `output_dbz`,
`output_winterp` must be on or generation refuses. **That is new safety the plan did
not have:** it catches a run that burns hours and only then turns out to have
written no `dbz`.

### 10.2 Line-anchored text substitution, not parse-and-re-emit

Two failure modes, killed by one decision:

- **Substring clobber.** An unanchored `dz` match also hits `dz_bot`/`dz_top`; `dx`
  hits `dx_inner`/`dx_outer`. The corrupted deck still *runs* — it just isn't the
  simulation that was asked for. Anchoring on `^\s*KEY\s*=` prevents it, and the
  negative-control suite proves the risk was real (3 `dz`-containing lines).
- **Float round-tripping.** Parse-and-re-emit would have to round-trip
  `rdalpha = 3.3333333333e-3`, `ccn = 0.6e9` and the inline `!` comments in
  `&nssl2mom_params` through float formatting, rewriting 400 lines to change 17.

Result: **396 of 413 lines are byte-identical to the template**, and 410 of 413 are
byte-identical to the committed hand-written deck. The 3 remaining are pure
formatting (`dtl = 3.0` vs `3.000`; one space of alignment on `dx_inner`/`dy_inner`).

**The claim this earns is "reproduces the run", not merely "reproduces the deck".**
All 3 residual diffs are insignificant in Fortran namelist free-format — both sides
parse to the identical REAL, and leading whitespace is ignored. With `isnd=5` the
Weisman–Klemp sounding is computed internally, so the namelist is CM1's *sole*
scenario input; there is no external sounding or seed file to diverge. Therefore the
generated deck, run with the same binary and rank count, produces a **bitwise-identical
run**, inheriting the Phase 0 reproducibility verification — no re-run needed to
establish it. That is exactly what the charter's data policy leans on when it makes
"regeneration from `sim/` + `pipeline/`" the recovery path for un-backed-up packages.

### 10.3 The gate is non-circular by construction

The template is the **Phase 0 validation deck**, not a copy of the target. All 17
scenario keys genuinely differ between template and target, so reproducing
`single_cell_500m` exercises every substitution rather than no-oping against itself.

**Gate result: PASS — all 344 keys match** the committed
`sim/single_cell/namelist.input` by parsed value, modulo comments and key ordering.
Comparison is by value, not text, because the hand-written decks are not
column-consistent (` ptype     =  5,` vs ` ptype     =  27,`) — a byte gate would
fail on whitespace while proving nothing about the physics.

### 10.4 Negative controls — 12/12

A gate that has only ever passed is not yet known to work (the same objection the
advisor raised against T1's never-fired `_validate`). So each guard was made to
fire:

| Control | Result |
|---|---|
| Generated deck vs *wrong* reference (Phase 0 deck) | 24 keys differ = 17 scenario/derived + 7 output-block — comparator is not vacuous |
| `dz`/`dx`/`dy` vs `_bot`/`_top`/`_inner`/`_outer` | neighbours intact; risk confirmed real |
| Missing `ptype` / missing `iwnd` / typo'd key | all refused |
| `imove=0` with `umove=12.5` | refused as a contradiction (it would also break the static SVT bbox centre) |
| `imove=1` without `umove` | refused (Bunkers estimate is not derivable); accepted when supplied |
| `output_dbz=0` / `output_winterp=0` | refused |
| `nx=200, dx=333` | `tot_x_len` → 66600, `dx_inner` → 333, `dx_outer` untouched |

**Caveat, same as T1b's:** this proves *faithfulness* for the one existing scenario.
Cross-scenario generalization still rides on T6 — that is what first exercises the
generator against a config it was not reverse-engineered from. This is the honest
boundary rather than a soft spot: with exactly one hand-written reference deck in
existence, T1c *structurally cannot* prove more. Every future scenario's deck **is**
the generator's output, so there is nothing independent left to compare against.

### 10.5 Forward pointer: what T6 may cheaply change

The generator rejects unrecognised keys, so a second scenario may differ **only** in
the 22 `REQUIRED_KEYS` plus `umove`/`vmove`. This bounds what "cheap variant" can mean:

| Variant | Cost |
|---|---|
| Resolution / domain size (`nx`, `dx`, `timax`, …) | **Free** — already in `REQUIRED_KEYS`. |
| Domain motion (`imove=1` + Bunkers `umove`/`vmove`) | Free; the branch is already tested. |
| **Seed** variation (`irandp=1`) | Needs a seed key added to `REQUIRED_KEYS`. |
| **Bubble** geometry/amplitude | Likely `init3d.F` — **code, not namelist**. |
| **Sounding thermodynamics** (CAPE/CIN) | The charter's modified-sounding-generator task. Not a namelist edit. |

So the cheapest honest single-cell variant is a **grid/domain change**; anything
thermodynamic is more than a config edit. That, plus the generic `run_scenario.sh`
deferred below, is T6's real setup cost.

### 10.6 Follow-up, deliberately not done here

`sim/single_cell/run.sh` still hardcodes its run dir, rank count and provenance
strings. A **generic scenario runner** (`run_scenario.sh <name>`: generate deck →
stage binary → run → write `run_meta.txt` from the JSON) belongs to **T6**, which is
the first task that actually needs it. T1c's scope was the deck and its gate.

## 12. T2 — manifest `web` block + `format_version` 1.1 (DONE 2026-07-20)

Phase 1 carried item #2, discharged. `manifest.json` now declares that `web/` belongs
to the package, so the package is self-describing instead of leaving
`web/web_manifest.json` standing alone. **No re-export** — exactly what the carried item
promised.

### 12.1 The block is a POINTER, not a census — and that is the whole design

The first design had `manifest.build(sc, frames, provenance, web=...)` fed from the web
export, a `link-web` subcommand to attach it to an already-shipped package, a
cross-manifest consistency check (grid, source run, frame list), and a negative-control
suite. The advisor killed all of it on one fact already in evidence:

> `web/` is **gitignored**; `manifest.json` is **tracked**. On a fresh clone `web/` is
> absent until regenerated.

So any grid/frame/byte figures copied into the tracked manifest would be false on a fresh
clone and stale after the next re-export, while `web_manifest.json` remains authoritative
for all of them. **A copy needs a consistency check; a pointer does not — nothing is
duplicated, so nothing can drift.** The consistency machinery existed only to police a
duplication that should not have been created.

What the block therefore carries: `dir`, `manifest`, `web_format_version`, `consumer`,
and prose for `content` / `authority` / `presence`. What it deliberately does **not**
carry: grid, frame count, per-frame records, byte totals, qmax. `presence` states the
distinction explicitly — the block declares that the rendition *belongs to* the package,
not that the files are on disk right now.

Consequences that fall out for free, all of which the rejected design had to work for:

- No ordering problem. `export` writes `manifest.json` *before* `export-web` runs; a
  census would have had nothing to census. A static declaration does not care.
- `manifest.build()` stays a **pure function of (Scenario, frames, provenance)** — which
  is the property the whole gate rests on (§8).
- No new subcommand, no auto-invoke hook between the two export commands.

### 12.2 The versioning rule is now written down, not inferred

`contract.FORMAT_VERSION` 1.0 → 1.1, and the bump rule was made explicit at the same
time rather than left to the next person's judgement:

- **MINOR** — additive and back-compatible; new keys a 1.0 reader can ignore while still
  rendering correctly.
- **MAJOR** — anything a reader cannot ignore: channel names/order, the SVT texture map,
  encodings, the transform/units contract, package layout.

This is load-bearing right now, not bookkeeping. §7 froze the UE-facing contract because
an SVT import re-test **cannot happen this phase** (owner-gated editor; `-nullrhi`
structurally cannot validate render). A minor bump is safe precisely because it changes
nothing a 1.0-era reader relies on — and the gate below proves that rather than asserting
it.

`WEB_FORMAT_VERSION` also moved into `contract.py` (webvol re-exports it, the same
pattern T1 used for `SVT_TEXTURE_MAP`): it is frozen by the format contract, not chosen
per scenario. It stays at **1.0** — the brick layout, quantization and reader contract
were untouched, and `diorama/src/volume.ts:40` refuses a newer *major* on that field.
The diorama never reads `manifest.json` at all, so the package bump is invisible to this
phase's only player.

### 12.3 Gate — the T1b diff, not a new control suite

Because `build()` stayed pure, T1b's method applies verbatim: rebuild the shipped 48 KB
manifest from committed inputs (scenario config + the shipped frame/provenance records)
and compare. Two gates, both PASS:

| Gate | Method | Result |
|---|---|---|
| A — structural | Recursive diff of rebuilt vs. shipped | **PASS** — exactly **2** differences: `format_version` `1.0`→`1.1`, and the added `.web` key. Plus a pointer check: no census keys present. |
| B — byte | Revert those two changes on the rebuilt doc, re-serialize, compare bytes | **PASS** — **34810 chars byte-identical**, the same figure T1b gate A recorded. Nothing else moved, including key order and float formatting. |

Gate B is what makes the claim precise. "Only two things changed" from a structural diff
would still permit a reordered key or a reformatted float; byte-identity after reverting
the two intended changes does not.

The shipped manifest was then regenerated in place (34810 → 35860 chars) — no CM1, no
netCDF, no VDB touched. `git diff` on the tracked file confirms both gates from a third,
independent direction: **1 line changed, 9 added, 0 removed.**

**Method gotcha, cost ~2 minutes but would have polluted the diff:** the rebuild was run
under *Windows* Python, whose text-mode write turned 1932 LF into CRLF in a file the
pipeline writes from *WSL*. Both gates still passed — they compare strings read in
universal-newline mode, which is blind to it — and git would have normalized on commit
anyway, but the working file would no longer have matched what the exporter produces.
Rewritten as LF. The same applies to `web_manifest.json`. **Any in-place edit of a
package file from Windows must be byte-mode**, since the pipeline that owns those files
runs in WSL.

### 12.4 The gate is now standing, not one-shot

`pipeline/tests/test_manifest.py` (7/7 pass) promotes T1b's one-time trick to a permanent
gate, so a future edit to `manifest.py` that silently perturbs the shipped contract fails
in the test instead of in UE:

- rebuild is byte-identical to the shipped manifest (T1b's invariant, standing);
- the export grid derives from the scenario crop box;
- `format_version` is 1.1 and agrees with `contract.py`;
- the web block agrees with the `contract.WEB_*` constants;
- the web block is a pointer — an explicit **census-leak check** on `frames`,
  `frame_count`, `grid`, `channels`, `bytes`, `qmax`, `voxel_m`, `dimensions`;
- **no census in PROSE either** (added on advisor review — see below);
- `web_format_version` was **not** bumped;
- the 1.1 bump is purely additive — the 1.0 key set is intact and `web` is the only
  addition.

This only works because `scenarios/**/manifest.json` is tracked (the charter's data
policy): the test reads committed files exclusively — no CM1, no WSL, no network. That
tracked-manifest decision is now paying a second dividend beyond being a version-
controlled contract. T1c's 13 deck controls still pass, unaffected.

`web/web_manifest.json`'s `package_format_version` mirror field was patched 1.0 → 1.1 for
on-disk coherence (with the same revert-to-bytes gate). It is gitignored and regenerated
by the batched T3–T5 re-export; nothing is built on it.

### 12.5 A census in prose is still a census

Caught on advisor review *after* the first commit, and it is the exact drift the pointer
design exists to prevent. The `content` field read:

> "…**two files per frame** (`fNNNN.rgba.gz` = cloud/ice/rain/graupelhail;
> `fNNNN.dbz.gz` = the dBZ diagnostic)"

That is a census — just spelled in English, where the structured key check could not see
it. And it is **not stable**: §7 makes `w` web-export-only and *signed*, so it cannot ride
in the 4-channel rgba plane; at T4/T5 the file list grows and "two files per frame"
becomes false in a **tracked contract file**, silently, because nothing was watching. The
prose now points at `web_manifest.json` instead of restating it.

The lesson was turned into an **8th standing gate** rather than a comment: a regex guard
over every string in the web block, rejecting brick filenames and per-frame layout claims.
It was run against the pre-fix manifest first and **fired** (`PROSE CENSUS: content: 'two
files per frame'`) before the fix made it pass — so it is a control known to work, not
merely one that has never failed (the same standard T1c's §10.4 set).

## 13. T3 — dBZ resampled in linear Z (DONE 2026-07-20)

Phase 1 carried item #3, closed. `cm1post/regrid.py` grows `resample_dbz`; both dbz
call sites in `export_scenario.py` route through it; `contract.FORMAT_VERSION` → **1.2**;
`manifest.diagnostics.dbz` gains a `resampling` key and its `caveat` is rewritten.

### 13.1 The error was 13 dB, not a rounding blip

dBZ = 10·log₁₀(Z) is logarithmic, so averaging it is not averaging reflectivity.
Between neighbours at 20 and 40 dBZ the physically correct midpoint is
10·log₁₀((10²+10⁴)/2) = **37.03 dBZ**; interpolating in dB gives **30.0** — a 7 dB, 5×-in-Z
underestimate, always in the direction that hollows echo cores and smears their edges.
Measured on real frame 150 the peak correction is **+13.35 dB**, and **6.53 %** of export
voxels move (this export upsamples 2× from a 500 m run, so almost every voxel is
interpolated). Cosmetic in Phase 1; load-bearing now that the radar view ships.

`resample_dbz` is a **separate function, deliberately** — folding Z-space into the generic
`resample()` would corrupt the four mixing-ratio channels that share it.

### 13.2 The gate had to be positive, because §9 says byte-identity breaks here

T1b/T2's byte-identity trick is unavailable by construction. `pipeline/tests/test_regrid_dbz.py`
replaces it with three positive gates, **10/10 with negative controls**:

| Gate | What it pins |
|---|---|
| Hand-computed midpoint | 37.03 (new) **and** 30.0 (old) — fails if the transform is dropped *and* if applied twice |
| **Jensen invariant** on a real frame | 10log₁₀ is CONCAVE ⇒ `new ≥ old` **everywhere**, equality only at grid points. A whole-field property no merely-different resampler can satisfy |
| No inflation | interpolated Z ≤ max contributing Z ⇒ resampled max ≤ source max. This is *why* the web `qmax` (scanned on the CM1 grid) stays a valid bound and **why T3 cannot grow the bbox** |

The Jensen gate is an **inequality**, and `new ≥ old` also holds when new *is* old — so its
negative controls (no-op change; correction applied backwards) are not decoration, they
are the only thing separating it from a gate that always passes.

The bbox sweep is untouched regardless: it computes `active_mask` on the **native CM1
grid**, pre-resample (`export_scenario.py:56`).

### 13.3 `format_version` stays **1.1** — a data change is not a format change

T3 first bumped it to 1.2; the advisor flagged that as scope creep past §9 (which scoped
the manifest deliverable to rewriting `caveat`, no bump), and the owner delegated the call.
**Reverted.** The rule is about **format compatibility**: MINOR = additive keys a reader can
ignore, MAJOR = something it cannot. A dbz *value* change is neither — no channel name,
order, encoding, texture map or layout moved, so a 1.0-era reader renders a linear-Z package
correctly and **§7's SVT freeze holds untouched**.

The bump's stated purpose — "so a consumer can tell a linear-Z package from a dB one" — was
**redundant with the `resampling` key added in the same change**: a consumer reads
`diagnostics.dbz.resampling`, not the top-level number. And it cost real scaffolding: a
contract-vs-shipped skew hardcoded into two gates, both designed to fail at re-export and
needing hand-editing then. **A version number that moves for data changes stops meaning
"format".**

### 13.4 The shipped package is deliberately left stale

Per §9 the 301-frame re-export is batched behind T4 and T5. Regenerating `manifest.json`
now would advertise linear-Z dBZ over dB-resampled bricks — a manifest that lies. So the
tracked manifest is left alone and `test_manifest.py`'s byte gate uses T2's trick one more
time: name the **two** expected differences (`diagnostics.dbz.resampling` added, `caveat`
rewritten), revert them, require the remaining bytes identical. "Only two changes" alone
would still permit a reordered key or a reformatted float; reverting and comparing bytes
does not. **7 new negative controls fire**, including a same-length unrelated edit (35838
chars either way) that a length check would miss, and both directions of an unwanted
`format_version` bump. At re-export the revert block is deleted and the gate collapses
back to plain byte-identity. `test_manifest.py` is now **15/15**.

## 14. T4 — updraft `w` as a selectable field (DONE 2026-07-20)

`w` ships in the **web rendition only** (§7). `contract.CHANNELS` and
`SVT_TEXTURE_MAP` are untouched, so no SVT import re-test is owed. The viewer-side
layer is **T8**; T4 is the exporter, the encoding and the gates.

Source is `winterp` — w already interpolated to scalar points by CM1, i.e. the same
grid as the hydrometeors. **No destaggering**; the raw staggered `w` on `zf` is ignored.

### 14.1 `w` violates three assumptions the channel path is built on

This is why it needs a second path rather than a sixth channel, and each violation
cost a decision:

| | The five channels | `w` | Consequence |
|---|---|---|---|
| Sign | non-negative by definition | **signed** | needs `regrid.resample_signed` |
| Density | ~0 almost everywhere | **nonzero nearly everywhere** | no threshold, no zero sentinel |
| Span | ~1e4 → log encoding | ~1e2 | linear encoding is fine |

**The signed one is the load-bearing hazard.** `regrid.resample` ends with
`np.clip(out, 0.0, None)` — correct there, catastrophic here: routing `w` through it
zeroes **every downdraft**. It would not crash, warn, or look obviously wrong; it
would render a storm whose air only ever goes up. So `w` gets its own entry point,
not a flag on the shared one that a future caller can forget to pass. Same reasoning
as T3's `resample_dbz`, same shape of bug: *a shared resampler encodes an assumption
that one field violates.*

### 14.2 Encoding — signed uint8, symmetric about code 128

`v = 128 + round(127 * clip(w, ±scale) / scale)`, codes 1..255, **code 0 never occurs**.

Rejected: an affine map over the observed `[wmin, wmax]`. It uses every code, but
`w = 0` then lands on a **fractional** code — measured on this run's actual range
(−28.78 … +52.50), zero encodes to code 91 and decodes back to **+0.02 m/s**. That
paints a thin band of false vertical motion along the updraft/downdraft boundary,
which is the one feature a viewer actually reads off this field. Pinning zero to an
exact integer code costs only unused negative headroom.

**The scale is FIXED cross-scenario at ±80 m/s, not fitted per sequence.** Same
colour = same m/s in every package, which is what makes updraft strength comparable
by eye — and T6 exists precisely to put two scenarios side by side. 80 is empirical
headroom, not a round number: this cell peaks at **+54.8 m/s** but the Phase 0
validated supercell reached **+60.6 m/s** (docs/phase0-validation.md), so a
per-sequence scale would *already* disagree between two runs this project has made,
and a 60 m/s fixed scale would *already* clip one of them. Resolution is 0.63 m/s per
code. The exporter **errors** (never silently clips) if a sequence exceeds the scale:
raising it re-colours every existing package, so it must be a deliberate contract edit.

No deadband is baked into the byte. "|w| < ε is transparent" is a **render-time**
decision for T8; baking it in would discard weak-w data irreversibly at the wrong layer.

### 14.3 Measured — the crop caveat states a number, not a vibe

`w` is cropped to a box **sized on condensate** (26 km half-width, 18 km top, vs the
80 km CM1 domain — the box covers 38% of CM1 voxels). Vertical motion exists outside
it, so the honest question is how much. Swept over all 301 frames:

| threshold | voxels | outside box | clipped | peak clipped |
|---|---|---|---|---|
| \|w\| ≥ 0.5 m/s | 25 989 280 | 2 814 256 | 10.829 % | 6.30 m/s |
| \|w\| ≥ 1 m/s | 10 605 240 | 267 224 | 2.520 % | 6.30 m/s |
| \|w\| ≥ 5 m/s | 880 904 | 40 | **0.005 %** | 6.30 m/s |
| \|w\| ≥ 10 m/s | 318 260 | **0** | **0.000 %** | — |

Every storm-scale updraft and downdraft is inside the box; what is clipped is broad,
weak environmental subsidence (and never more than 6.3 m/s anywhere outside). **The
box was NOT resized** — it is shared with the VDB rendition, whose bbox centre must
stay static across the sequence for the SVT contract. The caveat is recorded in
`web_manifest.json`, pointing here for the numbers rather than copying them.

### 14.4 Gates

`pipeline/tests/test_regrid_w.py` — **10/10**. Byte-identity is unavailable (T4 adds
output by design), so the gates are positive, as in T3:

- **A purely-negative field survives resampling** — the anti-regression against the
  §14.1 hazard. It also *demonstrates the failure*: the same field through
  `regrid.resample` comes back `+0.000`, so the gate is not merely asserting that
  today's code does what today's code does.
- w = 0 decodes to **exactly** 0.0; quantization never flips a sign; round-trip error
  ≤ half a code; codes 1..255 span exactly [−scale, +scale].
- Linear interpolation cannot overshoot either bound — which is what keeps the
  manifest's `observed_min`/`observed_max` valid *after* resampling, the same role
  no-inflation plays for the dBZ `qmax` bound in T3.
- **3 negative controls**, each rejecting a design T4 actually considered: the affine
  encoding (fires — zero lands at +0.02 m/s), a per-sequence scale (fires — code 200
  means +29.76 m/s at this cell's peak but +34.36 m/s at the supercell's), and reuse
  of the generic resampler (fires — the silent downdraft zeroing).

**End-to-end on real CM1 data** (frames 150:152): 3 files per frame; the `w` brick
round-trips to within exactly the half-quantum (0.3150 m/s) of the resampled source;
**235 048 negative voxels** present in frame 150, i.e. downdrafts genuinely survived
the pipeline; code 0 never occurs. `w` costs ~0.09 MB/frame gzipped (~27 MB over the
sequence).

**T4 is provably additive on the data, too:** the `rgba` bricks for frames 150–152 are
**byte-identical to the shipped package**, while `dbz` differs by up to 51 codes —
which is T3's linear-Z correction, exactly where §9 says the break belongs.

### 14.5 The version question — and why it splits from T3

`WEB_FORMAT_VERSION` **1.0 → 1.1**. `FORMAT_VERSION` (package) **stays 1.1**.

The distinction that settles every version question in this project:

> **T3 changed dbz VALUES inside existing files → DATA → no bump.
> T4 adds a per-frame file, a manifest block and an encoding → FORMAT → MINOR bump.**

Not bumping would assert that "1.0" and "1.0-with-an-updraft-field" are the same
format. Bumping MAJOR would be worse: `diorama/src/volume.ts` refuses a newer major,
so it would lock out the very viewer T8 is about to extend — and a 1.0-era viewer
genuinely still renders a T4 package, because it never fetches the file it does not
know about. `SUPPORTED_MAJOR = 1` was checked, not assumed.

This bump avoids T3's trap of being **redundant with a key added in the same change**:
the version declares the **generation**, the `extra_fields.w` block declares the
**capability**. **T8 must feature-detect on the key, not on `version == 1.1`.**

### 14.6 T4 is the first time `contract` moves AHEAD of the shipped package

T3 was easy here only because it correctly declined to bump anything. Three gates in
`test_manifest.py` assumed `shipped == contract` on the web version, which held
through T3 and breaks the moment the constant moves while the package stays stale
(re-export batched, §9). The non-obvious one was **`gate_web_block_present`**, which
asserted the equality directly and has no revert mechanism — it would have failed for
the right reason at the wrong place. Resolution: paths are structural and must agree
now; the version skew is a **named, expected difference** — `gate_web_block_present`
pins shipped at the stale 1.0, `gate_web_version_bumped` gates the *contract* at 1.1,
and the byte gate's revert list grows a third entry. Two new negative controls cover
the inverse errors (version left un-bumped as the format grew; version bumped MAJOR).
`test_manifest.py` is now **17/17**.

## 15. T5 — composite reflectivity as a 2D plan product (DONE 2026-07-20)

`cref` ships in the **web rendition only** (§7), like `w`. The viewer-side radar plan
view is **T9**; T5 is the exporter, the encoding and the gates.

### 15.1 The blocking measurement came first

Everything below rests on one assumption — that CM1's `cref` is the column max of the
*same* reflectivity operator as the 3D `dbz` variable — so it was measured before any
code was written, over all 301 frames of the Phase 1 run:

> `cref` is **BITWISE identical to `dbz.max(axis=0)`** in every frame. Worst
> `|cref − colmax(dbz)|` = **0.000e+00**; both sequence maxima are **72.213715 dBZ**.

That is stronger than "equal to rounding", and it buys three things: `vmax` can be
borrowed from the dbz channel as an **identity** rather than a safe bound; the
ordering invariant below is licensed; and the shared NWS colormap is exact in both
views. Had it come back unequal, the whole design would have changed — which is why it
was a gate on starting, not a check at the end.

### 15.2 Option (b) was rejected: cref is CM1's, not ours

The tempting alternative was computing cref as the column max of the **exported**
(cropped, resampled) `dbz`, which would be trivially consistent with the 3D layer.
Rejected: that silently redefines a standard radar product to mean "composite
reflectivity of the part we happened to export". It is also **biased low and always in
the same direction** — the negative control measures −3.01 dB on a case where the
argmax level varies horizontally. The charter's rule that diagnostics come from
published parameterizations applied to simulated fields points the same way: take
CM1's.

### 15.3 The ordering invariant, which does double duty

```
resampled cref  = interp_xy( max_z Z )     "max then interpolate"
colmax of vol   = max_z( interp_xy Z )     "interpolate then max"
==>  cref >= colmax, never the reverse
```

It holds because the horizontal interpolation weights are shared across every z level
and are convex. Crucially it holds **in linear Z** — so the gate that checks it is
simultaneously the physical invariant *and* a detector for cref having been sent
through a dB interpolation. Measured on real frames: **0 ordering violations**, max gap
**+2.01 dBZ**, mean over echo cells +0.32 dBZ.

`resample_dbz_2d` is deliberately a **near-duplicate** of `resample_dbz`, not a shared
core both call. The dimensionality differs but the assumption is identical, and
`resample_dbz` sits under the passing T3 gate that was the entire point of T3:
refactoring validated code to share a core with new, ungated code puts the old gate's
subject at risk to save nine lines.

### 15.4 A separate dict and block, because the difference is RANK

`WEB_PLAN_FIELDS` / `plan_fields` are separate from T4's `WEB_EXTRA_FIELDS` /
`extra_fields` rather than a `dims` key inside them. Rank is the one thing a consumer
cannot discover from a raw brick: a viewer must know whether to allocate a 3D or 2D
texture *before* it reads the bytes, and a reader that branched wrongly would upload a
`ny*nx` buffer into a 3D texture — a silent garbage render, not an error. Two dicts,
two blocks, no branch.

### 15.5 The caveat, measured — and it changed the text

Drafted honestly but wrongly first: the caveat led with vertical truncation (cref is a
full-column max; the export box stops at 18 km). The 301-frame sweep says that concern
is **exactly zero** —

| | |
|---|---|
| levels dropped by the 18 km box top | 4 (18.25, 18.75, 19.25, 19.75 km) |
| worst cref lost to truncation, 301 frames | **0.000000 dBZ** |
| columns affected, summed over all frames | **0** |
| peak dbz **anywhere** above the box top | **0.0000 dBZ** |

There is no echo up there at all, so the truncation costs cref nothing in this
scenario. The entire cref-vs-volume gap is §15.3's resample ordering, which is a
correctness property of cref rather than a crop artifact. The manifest text was
rewritten to say so.

**Then rewritten again, because the first fix committed the T2 error one level over.**
The corrected caveat *asserted* its numbers — "over all 301 frames of this run the peak
dBZ above the box top is 0.0000", "~2 dB" — inside `build_manifest`, which is the
**generic per-scenario builder**. Those strings ship in *every* scenario's manifest, so
T6 would have emitted single_cell's figures into scenario #2's contract, where they may
be false. It also contradicted T4's own rule (§14.3: point at the doc, do not copy the
numbers), and the "~2 dB" was measured on **3 frames**, not 301 — run-specific *and*
undersampled. The prose now keeps only the **structural** claims (horizontal
losslessness by construction, the max-then-interp ordering), which hold for every
scenario, and points at this doc for every figure. Per-scenario numbers live in
`observed_min`/`observed_max`, which are computed.

The gates were blind to this — they check the package manifest's structure, not the web
manifest's prose — so `gate_no_run_specific_numbers_in_prose` was added, regex-matching
frame counts and dBZ figures in the `plan_fields` strings and **fired against the
pre-fix draft to prove it rejects it**. `test_regrid_cref.py` is now **13/13**.

Horizontally the crop is **lossless by construction** above the shared threshold: cref
exceeds it at (x,y) exactly when some dbz in that column does, and the box is sized to
contain every such voxel. `cref` therefore takes no part in `active_mask` and cannot
grow the bbox — a plan field has no z and cannot mark a voxel active.

### 15.6 Gates

`pipeline/tests/test_regrid_cref.py` — **13/13**, positive as in T3/T4. Two of them
were rewritten after first passing, for the reason this project keeps restating:

- **`gate_shares_the_dbz_scale` was a tautology.** It encoded the same values twice
  with the same arguments and compared them — it could never fail. The real claim is
  about the **wiring**, and a reader builds its colour ramp from the *manifest*, so the
  gate now goes through `webvol.build_manifest` and compares what actually ships. A
  fifth negative control breaks the wiring (`vmax_from='cloud'`) to prove it can fail.
- **`gate_midpoint_is_linear_z`'s "applied twice" arm was vacuous** — the double
  transform overflowed to `inf`, so the inequality held trivially. Replaced with the
  realistic half-applied mistake: forgetting the return leg, leaving a raw Z (5050.0)
  in a field labelled dBZ, which an encoder that only clips at vmax would pass straight
  through.

The other 3 negative controls each reject a design actually considered: dB-space
interpolation (−7.03 dB), colmax-of-volume as cref (−3.01 dB, §15.2), and a separately
fitted vmax (40 dBZ → code 133 shared vs 163 fitted — same dBZ, two colours, one
colormap).

The exporter also carries a **standing** version of §15.1's measurement: it fails the
export if a plan field's observed max exceeds the channel max it borrows. The identity
was measured on one run; that is not a property of CM1, and a future `ptype` where cref
is computed differently would otherwise silently mis-scale the whole plan view.

### 15.7 End-to-end on real CM1 (frames 150:152)

## 17. T7 — diorama scenario selection (DONE 2026-07-20)

The diorama played exactly one package: `vite.config.ts` hard-coded
`DATA_DIR = ../scenarios/single_cell_500m/web`, and `main.ts` fetched the one
`/data/web_manifest.json`. T7 makes the package a **choice** — a picker in the
control bar (or `?scenario=<name>`) — now that T6 shipped a second package with
a *different grid*.

### 17.1 The load-bearing decision: a switch RELOADS the page, it does not rebuild GL state

This is the whole design, and it turns on a fact the code already had: **the
viewer is grid-agnostic within a single load.** `nx/ny/nz`, `volumeBox` (origin
+ voxel from the manifest), the log-decode constants, the shadow-cache dims, and
the 24-slot texture ring all derive from the loaded `web_manifest.json`. The
*only* things pinning the app to one package were the hard-coded data dir and the
single manifest URL — both startup values.

The two packages differ in grid — `single_cell_500m` is **208×208×72 @ 250 m**,
`single_cell_333m` is **126×126×54 @ 333 m** — so every GL resource (24 volume
textures at 12.5 MB, the parallel dbz ring, 24 shadow caches, the box, the
uniforms) is sized to a grid **captured in the `start()` closure**. Two ways to
switch:

- **Rebuild in place** — factor all allocation out of `start()` into a
  `reinit(manifest)`, dispose and re-create every texture at the new size, reset
  the pool/streamGen/ready state. A large, error-prone refactor of a
  1000-line file, whose entire payoff is *not reloading the page*.
- **Reload with a new `?scenario=`** — every closure-captured grid constant
  re-derives from scratch, with **zero** risk of a half-updated GL state or a
  leaked texture. ~40 lines, and it matches the viewer's grain: it is already
  URL-param-driven at startup (`az`, `el`, `layer`, `sx`, `frame`, …).

Reload wins decisively. It is proportionate to what a scenario switch *is* — a
change of the whole dataset, categorically bigger than the in-frame `layer`
toggle (which correctly avoids a reload because it changes one texture binding,
not the grid). The switch **preserves every other URL param** (`scenarioSwitchUrl`
sets only `scenario`), so the current view and tuning survive it.

### 17.2 Server: `/data/<name>/` + `/scenarios.json`, enumerated per request

`vite.config.ts` now maps `/data/<scenario>/<file>` onto
`scenarios/<scenario>/web/<file>` and exposes `/scenarios.json`, which scans the
`scenarios/` root for any subdir carrying `web/web_manifest.json` and returns
`{name, voxel_m, nx, ny, nz, frames}` per package — read from each manifest, so
the picker labels are honest without a pipeline change (the web manifest carries
no scenario name/description; the dir name is the identity). Enumeration is
**per request** (a `readdir` + two small JSON reads), so a freshly exported
package appears in the picker without restarting the server.

**Security.** The scenario segment is the only sanitizer needed on the data path:
`^[A-Za-z0-9_.-]+$` and never a lone `.`/`..` excludes slashes and traversal, so
`<root>/<name>/web` is provably under the root; a `startsWith(base + sep)` guard
then blocks per-file traversal in the remainder. Verified directly: an encoded
`/data/single_cell_500m/%2e%2e/%2e%2e/vite.config.ts` is **rejected by the
handler** (it `next()`s). It still returns 200 — but the body is vite's
*transformed* config module (`import … from "/node_modules/.vite/deps/…"`), i.e.
**vite's own dev module serving**, not raw `fs` bytes from my handler; that is
universal vite-dev behaviour (any project `.ts` is reachable at its own URL),
dev-only, and not introduced by T7. The handler serves only real files under
`scenarios/<name>/web` (a legit brick returns `application/octet-stream` raw gz).

### 17.3 Viewer: a small pure module, unit-tested

The DOM/reload wiring stays in `main.ts`; the decisions are factored into
`src/scenario.ts` so they are testable off the GPU:

- `resolveScenario(param, available, preferred)` — URL param that is actually
  served wins; else the preferred default (`single_cell_500m`, the historical
  `DATA_DIR`, so old bookmarks keep their storm); else the first served package;
  else (discovery returned nothing — a production build with no dev middleware)
  a best-effort fall back to the param or the compiled default, so a single
  hand-placed package still loads.
- `dataRoot(name)` → `/data/<name>` (matches the server map).
- `scenarioSwitchUrl(search, next)` — set `scenario`, preserve all else.
- `scenarioLabel(s)` → `single_cell_500m · 208×208×72 @ 250 m`.

`main.ts` fetches `/scenarios.json` (best-effort; a failure just leaves the
default to load), resolves the scenario, routes the manifest and every brick URL
through `root = dataRoot(scenario)`, and populates the picker **only when ≥2
packages are served** (no false choice for a one-package checkout). Beyond that
routing, the viewer needed **no** change to render a different grid — which is
the §17.1 point made concrete.

### 18.1 The `w` render — a SIGNED field breaks the dbz template in three places

`w` streams exactly like the dbz plane (an R8 volume per ring slot, gated + lazy
so the hydrometeor default fetches/uploads/binds nothing extra — hydro stays
byte-identical), but it is **signed**, and that changes three things the dbz
path could assume away:

1. **Decode.** `value = (byte-128)/127*scale`, byte 128 EXACTLY 0 (the
   updraft/downdraft boundary is exact, not a rounded fraction that would paint
   false motion along the zero line). A CPU mirror `decodeSignedU8` was added
   next to `decodeLinearU8`, unit-tested for exact-zero, ±scale ends, and
   antisymmetry.
2. **Projection.** The dbz MIP is `max(dbz)`; `w`'s is the along-ray extremum by
   **absolute value** (`abs(w) > abs(wExt)`), keeping the sign — so a ray shows
   whichever of an updraft/adjacent-downdraft core is stronger. **Labeled
   honestly** as "peak |w| along each view ray, coloured by sign" (the 5b
   composite-reflectivity mislabel trap), NOT as a column-integrated field.
3. **Colour domain — the load-bearing decision (advisor correction).** The dbz
   shader normalizes by `man.dbz.vmax`, which differs per package (78 vs 72).
   Copying that for `w` would make the same red mean +67 m/s in the 333 m package
   and +55 in the 500 m one — silently breaking T4's whole reason for a FIXED
   ±80 scale ("same colour = same m/s") and defeating T6 cross-scenario
   comparison. So the `w` colour domain is driven by the **constant**
   `extra_fields.w.scale`, never a per-sequence max. `?wclip` sets a tighter
   *fixed* clip; `?wdead`/`?wramp` tune the transparent deadband + alpha ramp.

Palette: a colorblind-safe **coolwarm** diverging map (blue↔red through a light
neutral, no green), mirrored TS↔GLSL from one `W_STOPS` table exactly as the dbz
palette is — the parity is unit-tested (guards now allow negative `t`).

## 19. T9 — composite-reflectivity radar plan view (DONE 2026-07-20)

The last Phase 2 task, and the one §2.3 flagged as a labeling trap: the diorama
already had a "Radar (dBZ)" layer, and an earlier advisor caught that it is *not*
the radar view people mean — it is a maximum along the **view ray** (it changes as
the camera orbits), which equals composite reflectivity only looking straight down.
T9 ships the real thing — CM1's column-max `cref`, **view-independent** — and the
two must stay distinctly labeled. Viewer-only: the data was already shipped web-only
at web 1.2 by T5, and the SVT contract stays frozen (no owner-gated re-import owed).

### 19.1 The render decision: an in-scene ground map, not a 2D screen inset

`cref` is a 2D plan product, so the render is fundamentally different from the
dbz/w volume MIPs. Two candidate shapes:

- **A flat radar map painted on the toy landscape** — the diorama-native choice.
  It keeps the scale/place/terrain context the whole viewer is built around, and
  the cref *field* is genuinely view-independent, so showing it obliquely is
  honest.
- **A face-on 2D "radar screen" inset** — more literal, but throws away the
  diorama context and duplicates the DOM legend/scalebar machinery.

Took the ground map (advisor-endorsed). It **reuses the existing LDR-composite
pattern** (the dbz MIP and the 5a cut-face sheet already composite false-colour
after the tone map so on-screen colour equals the DOM legend exactly): after
tonemap, where the ray hits the rendered ground (`d < 1.0`) inside the storm
footprint, sample `cref(x,y)` and `mix` in the NWS colour. Sampling at the
**surface point** (not a fixed z-plane) is occlusion-free by construction — it
paints exactly where visible ground is — and drapes over Phase-3 terrain for free.

### 19.2 The load-bearing risk was the camera, not the render

An in-scene flat map at the viewer's default **11° elevation is an edge-on smear**
— rendering succeeds while the plan view *fails to read* as "the top-down product
from TV". So entering the cref layer **frames the camera near-overhead** (78°),
leaving azimuth/distance alone and orbit fully free afterward (the data is
view-independent — look from anywhere). Leaving restores the prior elevation; `?el=`
pins a capture angle and suppresses the auto-framing. This is the same class of
trap as the 5b MIP mislabel: getting the label *true to the eye*, not just to the
data. **Verified from a real overhead capture**, not assumed.

### 19.3 The uLayer=3 collision — bigger than the one obvious site

Adding a fourth layer value exposed that the existing `w` branches gate on
`uLayer > 1.5`, which cref=3 also satisfies. Four sites, not one, and the sneaky
one is the cut-face sheet: bounding only the w `else if` would have pushed cref
into the trailing `else` → **painting the viridis hydrometeor cut-face**. Fixed:
the w MIP loop and w LDR composite gain `&& uLayer < 2.5`; the sheet's trailing
`else` becomes `else if (uLayer < 0.5)` so cref (a plan product with no volumetric
cross-section) matches nothing there; and the TS `ViewKey` + `uLayer` uniform both
gain the cref→3 case so idle-accumulation resets on the toggle. Hydro (uLayer=0)
satisfies none of the new bounds and `uLayer < 0.5` in the sheet, so it is
**untouched by construction** — the bit-identical-when-off discipline holds without
a stash diff.

### 19.4 One colormap serves both radar views — by identity, not approximation

`cref` shares the dbz `(threshold, vmax)` and decodes with the **same** linear-uint8
map, so one byte means one dBZ in both and the shared NWS palette is exact. This is
licensed by T5's blocking measurement (§15.1): CM1's `cref` is *bitwise*
`dbz.max(axis=0)`, so the sequence maxima are equal by identity. The shader reuses
`uDbzThr`/`uDbzMax` (no extra scale uniforms); the exporter's standing check
(§15.6) is what keeps the identity true for a future `ptype`.

### 19.5 Streaming, feature-detect, labeling

A lazy ring of **2D** R8 textures (cref is a plane, ~43 KB/slot vs the volumes'
12.5 MB), fetched/decoded/uploaded parallel to dbz/w and gated by `crefActive` so
the hydrometeor default pays nothing. `crefBytes = nx*ny` is the **decompressed**
size — `frame.cref_bytes` is the gzipped figure, and `loadBrick` checks the
inflated length (a gotcha shared with dbz/w). The layer is **feature-detected on
`plan_fields.cref`** (charter: detect the key, not the version). The panel names it
"Composite reflectivity" against "Radar (dBZ)" so the §2.3 distinction is legible in
the selector itself; the DIAGNOSTIC badge is read from `plan_fields.cref.diagnostic`;
the HUD/legend state it is a view-independent plan product, explicitly unlike the
dBZ line-of-sight MIP.
