# Phase 3 plan — flat convective-regime scenarios (supercell · seed variation · multicell)

**Started 2026-07-20** on the owner's explicit go, immediately after Phase 2 closed
(`docs/phase2-plan-2026-07-20.md`, T9 = cref radar plan view). Advisor-reviewed before any
code was written; the framing it forced — a flat/terrain fork rather than a flat list of
four features — restructured the whole phase and is recorded in §2.

## 1. Scope, as pinned by the owner

The charter's Phase 3 line is four major features across a hard architectural fork. As with
Phase 2, each ambiguity was put to the owner before any planning:

| Question | Owner's answer | Consequence |
|---|---|---|
| Which flat-domain scenarios? | **Supercell + seed + multicell** | The full flat convective-regime set. Cheapest-first: supercell (near-free), seed variation (small), multicell (heavier — likely Fortran initiation). |
| Where does terrain go? | **Its own later phase** | Phase 3 is **flat-only**. The terrain-following→Cartesian regridding module, the diorama heightfield render path, the static full-size domain and the VHDX resize all move out of this phase. See §8. |
| Which player? | **Diorama-only again** | No UE app this phase. Everything Claude-verifiable on a real browser GPU. **Y-flip / carried item #1 stays deferred with UE**, not discharged here (§6). |
| Hero resolution tier? | **333 m overnight default** | The Phase 0 default tier; overnight-able on this machine. No 250 m flat-imove hero this phase. |

**Phase renumbering.** Splitting terrain out means the charter's original "Phase 3 =
multicell/supercell + seed + terrain" no longer matches. This document defines **Phase 3 =
flat convective regime** (supercell + seed + multicell); **terrain becomes its own phase**
(provisionally "Phase 3T", slotted before the charter's Phase 4 = lightning/hail/particles/
polish). The charter status section is updated to match.

## 2. Advisor framing taken

### 2.1 The spine is the flat/terrain fork, not a flat list of four features

Advisor item 1 (docs/advisor-review-2026-07-09.md) is the hard fact that structures the
phase: **`imove` and terrain are mutually exclusive.** CM1's `imove` translates the whole
grid at constant velocity; terrain is fixed to the grid by the Gal-Chen transform — you
cannot translate a grid with terrain bolted to it. So the two regimes are different pipeline
paths, not two items on one list:

- **Flat scenarios** (supercell, multicell, seed) — share the existing pipeline, *may* use
  `imove`/Bunkers, and the diorama already renders them (flat ground plane).
- **Terrain** — a different pipeline path (Cartesian regridding), a static full-size domain,
  a new diorama heightfield, and the only feature that touches *both* pipeline and viewer.

The owner's "terrain → its own phase" call is exactly this fork made into scheduling. Phase 3
is the clean flat half.

### 2.2 Supercell is a near-empty override set, not a shear-design task

The advisor guessed, and it was verified before scoping: **the deck generator's base template
IS the Phase 0 supercell validation deck.** `sim/templates/base.namelist.input` carries
`iwnd = 2` (the validated sheared wind profile), `imove = 1`, `umove = 12.5`, `vmove = 3.0`
(Bunkers right-mover motion). `single_cell` *overrides* these down to `iwnd = 0, imove = 0`
to get the zero-shear pulse cell.

So a supercell scenario mostly **stops overriding** the template — it is the cheapest task in
the phase, not a shear-design task. This is why supercell goes first (§5, T1). The classic
CIN-controllable-sounding design task (advisor item 7) is **not** pulled in: the WK sheared
sounding the template already uses is sufficient for a legible split supercell. CIN control
remains a future science-code task, unscheduled.

### 2.3 Multicell is a different *class* of work — Fortran, not namelist

The template initiates with `iinit = 1` — a **single** warm bubble. Multicell needs multiple
bubbles, line forcing, or low-level random perturbations (advisor Q5; charter "Multicell
initiation is a scenario-design decision"). A *second bubble* is not a namelist count on
stock CM1's analytic init — it is almost certainly an `init3d.F` edit. That has a consequence
T1c's reproducibility claim rests on and must not silently break:

> §10.2 of the Phase 2 plan earns "reproduces the **run**, not just the deck" from the fact
> that with `isnd=5` the namelist is CM1's **sole** scenario input, so a generated deck +
> same binary ⇒ bitwise-identical run, inheriting Phase 0 reproducibility.

Edit `init3d.F` and the binary is no longer the Phase 0 binary — the namelist is no longer the
sole input. So multicell (T5) must **commit/tag the modified CM1 source and record a fresh
binary sha256**, or the charter's "regenerate from `sim/` + `pipeline/`" recovery path quietly
stops holding for that scenario. This is called out now so it is designed in, not discovered.

### 2.4 The asymmetric asset's value here is the cref orientation discharge — NOT the Y-flip

Tempting but wrong framing, flagged by the advisor: a split supercell is the first
known-asymmetric storm this project has, which *sounds* like the asset carried item #1 (Y-flip)
has been waiting for. It is not. Carried item #1 gates **UE placement code** (`scale.y = -100`),
and the owner deferred UE again (§1). The Y-flip stays deferred with the UE app.

What the asymmetric asset **does** discharge is the **T9 cref orientation test** (Phase 2 plan
§19): the symmetric centred cell made an x↔y transpose pixel-identical, so orientation was
earned only from the write convention, with the independent test explicitly deferred to "the
Phase 3 asymmetric asset". That test is **diorama-side and real regardless of the player
decision**, and T1 delivers the asset for it (§5, T3).

## 3. Feasibility confirmed before planning around it

- **Template already holds the shear** — `iwnd=2`, `imove=1`, `umove/vmove` set (§2.2,
  verified 2026-07-20). Supercell is an override-deletion, not new physics.
- **Phase 0 validated the physics** — canonical WK supercell split into counter-rotating
  movers, peak w 60.6 m/s @ 83 min (docs/phase0-validation.md, PASS). The supercell scenario
  inherits a proven storm; the only open question is the export box (§4.1), not whether a
  supercell forms.
- **`REQUIRED_KEYS`** (`pipeline/cm1post/deck.py:59`) lists `irandp` but **no seed/amplitude
  value key** — so seed variation (T4) is a deliberate `REQUIRED_KEYS` addition, exactly the
  cost §10.5 of the Phase 2 plan predicted ("a seed variant needs a new required key").
- **`imove`/Bunkers branch is currently negative-controls only** (Phase 2 §10.4) — T1 is its
  first positive exercise. The generator already refuses `imove=1` without `umove`/`vmove`
  and forces them to 0 at `imove=0`; that guard becomes load-bearing here.

## 4. Central design decisions (to resolve at task time, flagged now)

### 4.1 The export box for a splitting / moving storm — the real T1 work

Every scenario so far was a **centred, stationary, symmetric** cell, which made the SVT
static-bbox-centre requirement hold trivially (box centred at (0,0)). A supercell breaks all
three assumptions and the box is where the work is:

- **Splitting.** The storm splits into a right and a left mover that **separate** over time.
  The box must contain both across all frames.
- **Motion.** With `imove=1` tracking the Bunkers right-mover, the right mover stays roughly
  centred while the **left mover drifts** in the moving frame. With `imove=0` both move across
  a static domain. Either way the union-of-active-voxels box is **no longer symmetric about
  (0,0)** — but the SVT contract needs the box *centre* static across frames, which is a
  weaker condition than "centred at origin". The box is a static, padded, possibly
  off-origin frame containing the whole swept storm.
- **imove decision, deferred to measurement.** `imove=1` shrinks the domain (faster) but adds
  left-mover-drift and needs a Bunkers estimate a priori; `imove=0` is simpler and driftless
  but needs a full domain. **Recommend: measure both a bbox sweep and the drift before
  committing** — do not pre-bake imove into the config. At 333 m overnight, a static full
  domain may be perfectly affordable and is the lower-risk default; imove is the optimization
  to reach for only if wall-clock demands it.

This is the same "measure the box, never match it" lesson T6 taught (Phase 2 §16.2), now with
a genuinely asymmetric storm instead of a symmetric one.

### 4.2 VDB export for a diorama-only phase

The pipeline exports **both** a VDB rendition (for the deferred UE app) and the web rendition
(for the diorama). This phase's only player is the diorama. Open question for each task:
**do we still export VDB?** Arguments both ways —

- *Skip VDB:* it serves only the deferred UE app; the static-bbox-centre requirement it
  imposes is a real cost for an asymmetric storm; nothing this phase reads it.
- *Keep VDB:* the box discipline (§4.1) is the same work either way; keeping VDB means the
  scenario is UE-ready the day UE returns, with no re-export; and the SVT streaming budget is
  a cheap sanity number to keep tracking.

**Recommend keeping VDB** (the box work is shared, and a UE-ready package costs little extra),
but this is explicitly an owner-adjacent call to confirm at T1 rather than assume. It does not
block starting.

### 4.3 Seed reproducibility contract (T4)

The charter requires every scenario record its seed(s), and Phase 0 verified bitwise
reproducibility. Seed variation makes this concrete: two scenarios identical but for the seed
must produce **different** storms (the whole point), while **the same** seed must reproduce
bitwise. T4 adds the seed key to `REQUIRED_KEYS`, wires `irandp=1` + the CM1 seed/amplitude
keys, and adds a gate that same-seed ⇒ identical deck (and, once run, records the seed in
provenance). The "different seed ⇒ different storm" claim is a *run* property, verified once on
real CM1, not a deck gate.

## 7. Standing method rules inherited

- **Physics through simulation.** Each scenario's character (split, multicell organization,
  seed-driven outcome) must fall out of its CM1 environment and initiation, never be scripted.
  Diagnostics (`dbz`, `cref`) never feed back. (Charter core principle 1.)
- **Any "it renders" claim comes from a real GPU** — the diorama on a real browser GPU with
  numeric verification where a number is available, never `-nullrhi` and never a
  non-foregrounded tab (Phase 1's most load-bearing lesson; Phase 2 §11).
- **Measure the box, never match it** (Phase 2 §16.2) — doubly important now that the storm is
  genuinely asymmetric (§4.1).
- **A gate that has only ever passed is not known to work** — negative controls fire, as in
  every Phase 2 task (§10.4, §13.2, …).
- **Reproducibility** — record seed(s), CM1 build (binary hash), rank count, decomposition;
  a modified binary (T5) gets a fresh recorded hash (§2.3).

## 8. Terrain — explicitly OUT of Phase 3 (its own phase)

Recorded so the boundary is deliberate, not an omission. The terrain phase owns:

- **New pipeline module** — terrain-following → Cartesian-z regridding, done properly in
  Python (CM1's built-in interpolation is self-described quick-and-dirty; charter constraint).
- **New diorama render path** — the viewer's ground is a flat plane today; real orography
  means an actual heightfield under the volume. Terrain is the one feature that touches both
  pipeline and viewer.
- **Static full-size domain** (no `imove`) → the 15–30 h wall-clock class (advisor item 2).
- **VHDX resize** — the 1024 GB ceiling must be raised before the first 250 m terrain hero
  run, bounded by M:'s ~72%-full headroom (owner's number).

None of this blocks Phase 3, because flat 333 m scenarios need none of it.
